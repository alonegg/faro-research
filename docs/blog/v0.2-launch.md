# v0.2：让答案像研究员写的，而不是 API 吐的

> 上周开源了 [Faro Research](https://github.com/alonegg/faro-research) v0.1。
> 一周不到收到反馈：「跑得动，但输出读起来像 dump 不像研报」。
> 周末重写了一版。这是 v0.2。
>
> **核心改动一句话**：把 dexter 真正的"报告精髓"——formatters / skills /
> meta-tool / memory / 严格输出规则——一次全部补齐。

---

## 上一版的问题

v0.1 跑通了 agent 闭环，但一个 PE_TTM 查询的回答会长这样：

```
贵州茅台（600519.SH）的最新估值数据：

PE_TTM（滚动市盈率）= 20.965100
PE（静态市盈率）= 21.065700
PB（市净率）= 6.401500
总市值 = 173,413,127.103 万元
PS_TTM = 10.069800
...
```

**没人想读**这种东西。数据在那，但解析压力全留给读者。

v0.2 同一个查询：

```
## 贵州茅台（600519）估值快照

| 指标 | 数值 |
|------|------|
| **PE_TTM** | **20.97×** |
| PE (静态) | 21.07× |
| PB | 6.40× |
| 股息率 TTM | 3.73% |
| 总市值 | **¥1.73 万亿** |

> 数据日期：2026-04-30 (Tushare)
```

**1/4 的字数，10 倍的可读性**。差别在哪？

## 关键改动 1：Result Formatters

dexter 有一个被低估的设计：每个工具不仅返回原始 JSON，还附带一个 formatter
函数，把 raw API payload 转成 LLM 友好的紧凑 markdown。

我之前的实现是 `json.dumps(raw_dict)` 直接喂给 LLM。LLM 要先解析嵌套字段、
理解单位、再决定怎么输出。token 浪费 + 注意力浪费。

v0.2 给所有 5 个 Tushare 工具写了 formatter（150 行 Python）。比如
`get_key_ratios` 返回的不再是嵌套 dict，而是：

```markdown
## 600519.SH 估值快照 (2026-04-30)

| 指标 | 数值 |
|------|------|
| **PE_TTM** | **20.97×** |
| PE (静态) | 21.07× |
| PB | 6.40× |
| ...

## 季度财务指标 (近 4 期)

| 报告期 | ROE | 毛利率 | 营收 YoY | 净利 YoY |
|--------|-----|--------|----------|----------|
| 26Q1 | **10.57%** | 89.76% | +6.54% | +1.47% |
| 25Q4 | **34.46%** | 91.18% | -1.21% | -4.53% |
```

数字单位（`万元 → 万亿`）、季度缩写（`20260331 → 26Q1`）、加粗关键值，全在
formatter 里完成。LLM 拿到的就是已经"消化"过的事实。

**Token 减 5–10×。响应质量肉眼可见跳一档。**

## 关键改动 2：严格输出规则

v0.1 的系统 prompt 只笼统写"用中文 markdown 关键数字加粗"。v0.2 抄了
dexter 的硬规则做法，把约束写得很具体：

```
- ¥1.73 万亿 不是 1,734,131,270,300 元
- ¥168.8 亿 不是 16,883,810,251.4 元（≥ 100 亿用"亿"）
- 单表 ≤ 3 列；数据多就拆多个小表
- 表头 ≤ 4 字
- 公司名首次写全称，后面用简称
- 单工具问答 ≤ 80 字 + 1 个小表
- 多工具综合 ≤ 250 字 + 2-3 个小表
- 不写"综上所述"段落
```

这种约束**比抒情式 system prompt 有效 10 倍**——LLM 更愿意服从硬数字规则
（"≤ 80 字"）而不是模糊形容词（"简洁"）。

## 关键改动 3：Meta-tool

主 agent v0.1 看到 5 个 finance 工具，每次都要自己挑、串行调。

v0.2 加了一个 `get_company_data` 元工具：natural-language query 进，自动 LLM
路由到子工具（resolve_ticker + key_ratios + three_statements + holder_trades）
**并行**执行，stitch 成一个 markdown 块返回。

主 agent 现在只看到 2 个 finance 工具：`get_company_data` 和 `get_stock_quote`。
context 干净，决策快，turn 数从 3-4 跌到 1-2。

实测「茅台估值 + 近 3 年三表」：v0.1 是 5 turn / 4 tool calls，v0.2 是
2 turn / 1 tool call（meta 内部 7 秒并行拉齐 3 个子工具）。

## 关键改动 4：Skills 系统

dexter 的 SKILL.md 是它能写出**像 BCG 报告**的关键。每个 skill 是一份
markdown checklist，告诉 agent 要做什么、调什么工具、怎么验证、怎么排版。

v0.2 实现了 SKILL.md 加载 + 一个 `skill(name=...)` 工具。3 个内建 skill：

- **dcf-cn**：A 股 DCF 估值（10Y 国债无风险利率、申万行业 β、Gordon 终值、
  3×3 敏感性矩阵、EV / TV-share / PE-band 三道合理性校验）
- **research-report**：完整个股研报（一句话结论 → 业务画像 → 财务画像 →
  估值 → 催化与风险 → 信号面）
- **screener**：行业筛选

实测「给我写一份贵州茅台的深度研报」——agent 自动调 `skill('research-report')`
拿模板，按 8 步走完，4 个 turn 输出 600 字 + 4 张表的研报，结构和卖方初级研究员
没法区分。

## 关键改动 5：Memory + SOUL/RULES

**v0.1 没有跨会话记忆**。每次对话 agent 都得现场问"你的风险偏好是什么"。

v0.2 加了基于 SQLite 的 memory subsystem：
- `data/memory/long-term.md`：用户长期偏好 / 目标 / 仓位约束
- `data/memory/daily/YYYY-MM-DD.md`：每日研究笔记
- `data/memory/identity/SOUL.md`：用户身份 / 投资哲学（自动注入 system prompt）
- `data/memory/identity/RULES.md`：硬规则（"每次给个股建议前必须查高管交易"）

3 个工具：`memory_search` / `memory_get` / `memory_update`。

实测：

```
$ faro-research "记住:我偏好高股息蓝筹股, 单股仓位上限 25%"
已存档。

$ faro-research "茅台符合我的偏好吗"
[agent 先调 memory_search, 然后 get_company_data]

## 茅台 vs 你的偏好
| 你的偏好 | 茅台实际 | 匹配? |
|----------|----------|:---:|
| 板块：银行/公用 | 白酒消费 | ❌ 偏离 |
| 高股息率 | 3.73% | ⚠️ 中等 |
| 大市值蓝筹 | ¥1.73 万亿 | ✅ |
| 低负债稳健 | 12-16% | ✅ |
...
```

**真正个性化的研究助手**——不是每次都从 0 开始。

## 顺手修的 4 个细节

- **每工具缓存 TTL**（snapshots 1h / statements 24h / listings 24h）。重复
  查询同一只票 0 ms 返回。
- **每工具 timeout**（10-20s）+ 部分结果。一个慢工具不再拖死整轮。
- **并发执行**：同 turn 内 concurrency_safe 的工具走 ThreadPoolExecutor
  并行（meta-tool 内部就靠这个把 3 个子调用做成 7 秒）。
- **rich vs compact 描述**：每个工具有 `description`（多段，注入 system prompt）
  和 `compact_description`（一行，token 友好场景）。
